## §1 Mission

Build the first v0 React surface shell for the C2 Live Control UI.

The UI must prove the live-play product loop:

```text
load server catalog/layout/state/events/jobs
→ render required Chat + Record
→ submit GM text through POST /api/live/query
→ show answer/classification/suggestions
→ refresh Record and optional module state
→ persist layout through PUT /api/live/surface/layout
→ recover layout after browser refresh
```

This PR should make DungeonBuddy feel like an at-table control surface, not a repo dashboard or file browser.

---

## §2 Product Non-negotiables

Carry these through implementation:

1. **Server is authority.** The UI does not read or write session files directly.
2. **Layout persistence goes through L3.** No localStorage-only layout authority.
3. **Chat and Record are required.** They cannot be disabled by the UI.
4. **Record remains complete.** Hiding optional modules never deletes or hides source events from the data model.
5. **Human labels first.** Show labels like `Storm weather`, `Road encounter`, and `Gate dilemma`; file paths appear only as provenance/source captions.
6. **No artifact dashboard as primary surface.** Avoid giant file tables, artifact inventories, or repo-path-first navigation.
7. **Boring controls over fancy drag/drop.** Toggle/reorder/slot move is enough for v0.
8. **No corpus writes.** Canon commits/corrections are events/jobs shown by UI, not inline corpus patches.

## §5 Implementation Contract

### Package choice

Use Vite + React + TypeScript unless the repo already has a stronger frontend convention by the time the worker starts.

Expected scripts:

```json
{
  "scripts": {
    "dev": "vite",
    "build": "tsc -b && vite build",
    "test": "vitest run"
  }
}
```

Testing libraries may include Vitest and React Testing Library. Keep dependencies minimal.

### API client

`src/api/liveApi.ts` must centralize all server calls. Components should not call `fetch` directly.

Required client functions:

```ts
getSurface(): Promise<LiveSurfaceResponse>
getEvents(since?: string): Promise<LiveEventsResponse>
getJobs(): Promise<LiveJobsResponse>
postLiveQuery(text: string): Promise<LiveQueryResponse>
putSurfaceLayout(layout: SurfaceLayout): Promise<{ layout: SurfaceLayout }>
```

Optional, if cheap:

```ts
resolveRoll(command: string): Promise<ResolvedRollResponse>
completeJob(jobId: string): Promise<{ job: LiveJob }>
rebuildPacket(): Promise<{ job_id: string; status: string; job: LiveJob }>
```

Base URL should default to same-origin and be configurable through a Vite env var such as `VITE_LIVE_API_BASE_URL`. Document this in the app README.

### Types

`src/api/types.ts` should define enough of the L3 contract for UI safety. Required shapes:

- `SurfaceModuleDefinition`
- `SurfaceModuleInstance`
- `SurfaceLayout`
- `LiveSurfaceResponse`
- `LiveEvent`
- `LiveJob`
- `LiveState`
- `LiveQueryResponse`
- `TurnClassification`

Keep types pragmatic. Do not attempt full JSON Schema codegen in this PR unless it is trivial.

### App bootstrap

On load:

1. Call `GET /api/live/surface`.
2. Call `GET /api/live/events`.
3. Call `GET /api/live/jobs`.
4. Render `SurfaceShell` from server catalog + layout + state + events + jobs.

Loading and error states must be visible and human-readable. Do not fail silently.

### SurfaceShell

`SurfaceShell` must:

- render modules by enabled `layout.modules`, ordered by `slot` and `order`
- always render required `chat` and `record` if present
- render an explicit unsupported-module placeholder for unknown `module_id`
- pass shared server state to modules
- refresh state/events/jobs after a successful query
- refresh surface after a successful layout save

Slots for v0:

```ts
"main" | "sidebar" | "bottom" | "overlay"
```

A simple CSS grid/flex layout is enough.

### Module registry

`moduleRegistry.ts` maps server catalog IDs to React components.

Minimum required mappings:

```text
chat -> ChatModule
record -> RecordModule
roll_stack -> RollStackModule OR now -> NowModule as proof optional module
```

If catalog contains modules without implementations, show `UnsupportedModule` with the human title and module ID. Do not crash.

### ChatModule

`ChatModule` must:

- provide a text input/textarea and submit button
- call `postLiveQuery(text)`
- show answer text
- show classification mode and event type, e.g. `fast_live / roll_result`
- show next suggestions if returned
- call a parent refresh callback after success
- display error state on failed request

Required seed smoke path:

```text
Weather 7. Caelynn Nature 19.
```

Expected visible output includes:

```text
Hail dent
fast_live
roll_result
```

### RecordModule

`RecordModule` must:

- render events from `GET /api/live/events`
- show timestamp, event type, summary, and latency mode/origin where present
- refresh after Chat submits successfully
- avoid file-path-first display
- handle empty event list gracefully

Polling is optional for v0. Manual refresh or refresh-after-query is enough.

### Proof optional module

Implement at least one optional module from server state.

Preferred: `RollStackModule` because the demo script expects roll-stack visibility.

Acceptable alternative: `NowModule` if Roll Stack shape is awkward.

RollStackModule should show human labels from packet/catalog/state where available. It should not read source files. If it cannot mark T-WX done from returned state yet, it may show pending/resolved status from state/packet and rely on Record for event truth.

### LayoutControls

`LayoutControls` must allow the GM to:

- enable/disable optional modules
- keep required `chat` and `record` enabled and visibly locked
- reorder modules in a slot, or provide up/down controls
- move modules between `main`, `sidebar`, `bottom`, `overlay`
- collapse/expand modules if supported by layout rows
- persist full layout through `PUT /api/live/surface/layout`
- show server validation errors if layout save fails

Do not implement drag-and-drop unless it is cheaper than buttons/selects. Buttons/selects are preferred for v0.

### Context lookup display

The UI should handle a `context_lookup` response differently enough that the GM can see it is not a fast roll result.

At minimum:

- Chat shows the mode badge `context_lookup`
- answer/diagnostics/provenance are visible if returned
- Record refreshes with context question event

Do not build retrieval UI in this PR.

## §6 Required Test Cases

Create focused tests under `apps/live-control-ui/src/`.

Use mocked `fetch` or a lightweight test helper. Do not require a live FastAPI server for unit tests.

Required tests:

1. `SurfaceShell` renders required Chat + Record from mocked `GET /api/live/surface` data.
2. Required modules cannot be disabled through `LayoutControls`.
3. Optional module can be disabled and saved through `PUT /api/live/surface/layout`.
4. Layout move/reorder control calls `PUT /api/live/surface/layout` with a changed full layout.
5. Chat submit calls `POST /api/live/query` and renders answer + `fast_live / roll_result`.
6. After Chat submit, refresh callbacks call events/jobs/state or surface refresh functions enough for Record to update.
7. Record renders an appended `roll_result` event summary.
8. Human labels render before file paths. At minimum assert `Storm weather` or another server/catalog label is visible and raw source paths are not used as primary module titles.
9. `context_lookup` response displays the mode distinctly from `fast_live`.
10. Unknown catalog module renders an unsupported-module placeholder instead of crashing.

If test tooling setup becomes too heavy, keep the tests smaller but preserve coverage of required modules, Chat submit, Record render, and layout persistence.
