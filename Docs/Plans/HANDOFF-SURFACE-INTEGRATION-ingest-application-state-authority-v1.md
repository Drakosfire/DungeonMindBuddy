## §0 Steward design ruling

The Of Conks assembled-product dogfood exposed two different Ingest truths:

1. durable extraction work had happened;
2. the mounted product looked only for worktree-local `GraphIngestRunManifest` files and therefore reported no runs.

SI-1 made that false-empty visible. SI-4 must remove the underlying authority mistake.

The repository already has the governing persistence decision. `ARCHITECTURE-application-state-layer.md` classifies `IngestRun status/review/provenance` as **Buddy durable application state** owned by the Ingest domain in the existing `dungeonbuddy_application_state` PostgreSQL database. It explicitly rejects path-backed product identity and names `ingest.*` as the target domain schema.

### Chosen disposition

**Canonical `ExtractionRun` lifecycle becomes APP-STATE PostgreSQL authority.**

```text
ExtractionRun identity / status / revision / scope / lineage / component claims
    → Buddy application-state PostgreSQL
    → schema: ingest
    → mounted reads/writes: database only

GraphIngestRunManifest
    → legacy recap packaging / compatibility artifact
    → may remain on disk while old Graph Review projection still consumes it
    → NOT durable product authority
    → NOT runtime preflight authority

candidate graph / source-span / telemetry / validation bytes
    → execution or processed-artifact bytes for now
    → referenced by exact digest + locator from the durable IngestRun
    → this slice does not redesign Asset/Source storage
```

This is a cutover, not a shadow store. After the switch, mounted canonical `ExtractionRun` reads and writes **must not fall back to** `out/registries/extraction_runs.json`.

### Why the existing APP-STATE database

Do not create an Ingest-specific DSN or database. Buddy already owns one transactional application-state substrate. Ingest receives its own domain schema and repository/service layer within that substrate, following the existing Content and Play pattern.

### What remains file-backed after this PR

This PR does **not** claim that every generated byte belongs in PostgreSQL. It moves user-relied-on Ingest run state away from files. Existing component files may remain locators for generated/processed bytes until a later storage slice earns a different home. Their existence is not run identity.

If implementation discovers that a component is itself user-relied-on durable product state that cannot truthfully remain an execution artifact, stop and rebrief rather than silently stuffing arbitrary blobs into `ingest.run` JSONB.

# §1 Mission and merge-ready invariant

## Mission

A fresh checkout/worktree connected to the same configured Buddy application-state database can discover the same canonical Ingest runs regardless of whether that checkout contains `out/registries/extraction_runs.json` or `out/graph_memory/runs`.

## Merge-ready invariant

> **After explicit adoption of existing canonical file-backed ExtractionRun records, APP-STATE PostgreSQL is the sole mounted authority for ExtractionRun identity, lifecycle, revision, scope, lineage, and component-reference claims; production extraction creates and mutates those records transactionally in `ingest.*`, canonical reads never consult the legacy file registry, runtime preflight reports database-backed Ingest READY/EMPTY/UNAVAILABLE/INTEGRITY truth, and legacy GraphIngest manifests remain compatibility artifacts rather than product authority.**

No automatic migration on FastAPI boot. No permanent file fallback. No dual-write steady state.

# §3 Normative implementation design

## §3.1 Database schema

Add the next single Alembic head after `20260825_0004`.

Create schema/table:

```text
ingest.run
```

The table is domain-specific, not a generic object store. It must represent the canonical `ExtractionRun` contract with first-class columns for identity/lifecycle/scope and JSONB only for bounded structured subobjects already present in that contract.

Required logical fields:

```text
run_id                  TEXT PRIMARY KEY
schema_version           TEXT NOT NULL
record_version           TEXT NOT NULL
source_artifact_id       TEXT NOT NULL
source_domain            TEXT NOT NULL
status                   TEXT NOT NULL
revision                 INTEGER NOT NULL CHECK revision >= 1
campaign_id              TEXT NULL
session_id               TEXT NULL
profile_id               TEXT NULL
components               JSONB NOT NULL
 diagnostics              JSONB NOT NULL
lineage                  JSONB NOT NULL
superseded_by_run_id     TEXT NULL
supersedes_run_id        TEXT NULL
created_at               TIMESTAMPTZ NULL
updated_at               TIMESTAMPTZ NULL
```

Use DB constraints/indexes where they strengthen existing `ExtractionRun` invariants without inventing new semantics:

- admitted status check from `ExtractionRunStatus`;
- self-reference rejection for supersession links;
- self-FKs for known predecessor/successor rows if they do not prevent the existing atomic supersede operation;
- uniqueness preventing two successors from claiming the same predecessor;
- indexes for source artifact, `(campaign_id, session_id, updated_at)`, and status.

Do not add an SQL FK to a future Source table that does not yet exist.

## §3.2 Application-state Ingest package

Create `src/application_state/ingest/` following the existing Play pattern:

```text
repository.py
  raw SQL only
  no commit
  row ↔ ExtractionRun mapping
  list/get/lock/insert/CAS-update/supersession primitives

service.py
  assert schema at head
  one user-visible mutation = one unit_of_work transaction
  create/get/list/update/supersede operations
  typed APP-STATE failures

__init__.py
  narrow public exports
```

Reuse the canonical `graph_memory.ingestion.extraction_run.ExtractionRun` model and transition validators. Do not create a second IngestRun DTO with competing lifecycle semantics.

Repository reads must validate row shape and lineage. External component-byte availability is **not database-row integrity**. Exact review/promote operations may continue to resolve and digest-check component locators at their owning boundary.

## §3.3 Mounted compatibility facade

`apps/live_control_server/services/graph_run_registry.py` keeps its existing public function names where practical so extraction/review callers do not all learn SQL persistence details.

After cutover it becomes a compatibility/domain facade over `application_state.ingest`, plus the existing evidence-resolution checks needed by `get_reviewable_extraction_run`.

Mounted functions such as:

```text
create_extraction_run
get_extraction_run
get_reviewable_extraction_run
update_extraction_run_status
supersede_extraction_run
```

must use APP-STATE PostgreSQL.

Delete/retire mounted file-registry lifecycle machinery:

```text
DEFAULT_EXTRACTION_RUN_REGISTRY_REL
_load/_load_unlocked/_save_cas as production persistence
registry_token / registry_mutation_lock for ExtractionRun state
```

A migration-only reader may know the old path. Mounted product code may not.

### No dual write

Production extraction must not write both PostgreSQL and `out/registries/extraction_runs.json`. Once the facade switches, the DB write is the durable write.

## §3.4 Explicit existing-state adoption

Provide one explicit, operator-invoked import from the legacy canonical registry:

```text
out/registries/extraction_runs.json
```

Follow the existing APP-STATE import posture:

- schema must already be at Alembic head;
- import is explicit, never FastAPI startup side effect;
- validate the whole source document before mutation;
- preserve exact run IDs, revisions, timestamps, status, scope, components, diagnostics, and lineage;
- import in one transaction;
- absent destination row → insert;
- byte/field-equivalent existing row → no-op;
- same run ID with differing durable fields → conflict and rollback;
- repeated import is idempotent;
- source file is not deleted automatically;
- after cutover the source file is inert historical/migration material.

The importer may live under `application_state.ingest` with a thin `scripts/` entry point. Do not leave a reusable production fallback loader in `graph_run_registry.py`.

## §3.5 Runtime preflight

Replace the required SI-1 Ingest check that currently treats `DUNGEONMIND_GRAPH_INGEST_RUNS_ROOT` / manifest discovery as authority.

New required check reads APP-STATE Ingest authority:

```text
DB reachable + schema current + 0 ingest runs
    → EMPTY (valid)

DB reachable + schema current + valid ingest rows
    → READY

APP-STATE unavailable
    → UNAVAILABLE

schema behind / ingest schema missing
    → NOT_READY

persisted row cannot be interpreted as canonical ExtractionRun / invalid lineage
    → INTEGRITY_ERROR
```

Preflight must not require `out/graph_memory/runs` to exist. It may report legacy manifest-root health only if explicitly downgraded to informational diagnostics; preferred v1 is to remove it from required assembled-runtime truth entirely.

## §3.6 Legacy GraphIngest manifests

Do not delete recap packaging or Graph Review compatibility in SI-4. `GraphIngestRunManifest` still supports the old Graph Review projection path and may continue to be produced as an execution/compatibility artifact.

But no new code may describe it as durable Ingest authority. SI-5 is where `/ingest` consumes coherent Surface Information over the DB authority and the compatibility path can be reduced further.

## §3.7 Generated component bytes

The durable row stores exact component-reference claims (`kind`, locator, digest, exists advisory flag) because those claims are part of `ExtractionRun`.

This PR does not bulk-store candidate graphs, raw model responses, span indexes, or source bytes in PostgreSQL. It also must not use a worktree path as product identity.

A missing component file for a REVIEWABLE exact run must fail at the exact review/evidence boundary; it must not make the DB catalog pretend that no run exists.

# §6 Required adversarial and product witnesses

A. **Fresh-worktree authority:** with APP-STATE DB containing run R and no `out/registries/extraction_runs.json` / `out/graph_memory/runs` in the current checkout, canonical list/get still sees R.

B. **No mounted fallback:** create/import R into DB, then write a conflicting/extra legacy file registry; mounted get/list remains DB truth and never merges/substitutes file records.

C. **No dual write:** production `create_extraction_run` / real production extraction creates DB state and does not create/update `out/registries/extraction_runs.json`.

D. **CAS lifecycle:** stale expected revision cannot overwrite current run; successful status mutation increments exactly once.

E. **Atomic supersession:** predecessor SUPERSEDED + successor creation + reciprocal lineage commit in one transaction; injected failure leaves neither half-applied.

F. **Import replay:** first import inserts; second identical import no-ops; conflicting same-ID import rolls back all changes.

G. **EMPTY:** current schema, zero rows, no legacy roots → preflight Ingest EMPTY, not NOT_READY.

H. **UNAVAILABLE:** configured APP-STATE DSN unreachable → typed preflight UNAVAILABLE; no file fallback.

I. **INTEGRITY:** malformed/invalid persisted row or lineage at the DB boundary → INTEGRITY_ERROR; never EMPTY.

J. **Missing component bytes are not false-empty:** DB catalog still exposes the run; exact reviewability/evidence resolution fails explicitly at its owning boundary.

K. **Legacy recap compatibility:** recap extraction may still emit GraphIngest packaging for current Graph Review, but canonical `extraction_run_id` resolves from DB and no canonical file registry is required.

L. **Existing assembled DB adoption:** run importer against the operator's configured `dungeonbuddy_application_state` using the current canonical file registry when present; record source count/imported/noop/conflict and DB row count without exposing DSN secrets.

M. **Migration lifecycle:** ordinary server boot does not run Alembic or import files; explicit schema upgrade + explicit adoption are required.
