- **Honest verdict:** dispatcher enforcement **did not lift TP1**. Total cohort commits across 18 expected appends went from 4 (Iteration 4: 1+3+0) to **4** (Iteration 5: 4+0+0) — same total, very different distribution and a worse cross-run failure mode. Run 1 was a clean enforcement no-op (zero rejections; the model issued matching commits on its own for 4/6 slugs) and replicated Iteration-4-style misses (lysandra beat-regex anchor + zero calls for karsemine/ephanna + dustwalker false positive). Runs 2-3 exposed a new dominant failure: because `pending_preview` is held in the dispatcher closure (one closure spans all 9 micro-turns of a `run_timeline_pass_per_slug_chain` call), any micro-turn that ends preview-only poisons the *next* micro-turn — the model's first call there gets bounced with the corrective JSON, and instead of re-issuing the matching commit (which would clear the slot and let the new slug's micro-turn proceed), the model interprets the rejection as an out-of-band wait state and emits a `needs_clarification` "please apply that commit" message. Then every subsequent micro-turn hits the same poisoned slot until the chain ends. The micro-turn boundary is opaque to the dispatcher; the model treats the boundary as a context reset and never re-redeems the leaked token.
- **Next dominant failure mode:** **cross-turn pending-preview leak** in chained micro-turns. Within a single micro-turn the contract works as intended — the rejection happens, but the model in this scenario is doing the violation on its very last response of the turn (writing diff into `message`), so there's no in-turn rejection to react to. The reaction happens at the start of the *next* slug's micro-turn, where the carried-over pending-preview is unrelated to the new slug and the model can't construct the matching commit because it doesn't have the previous slug's args anymore (the model resets its working memory between slugs in our prompts). **Cheapest next lever:** clear `pending_preview` at the start of each new `run_planning_turn_detailed` call (i.e., scope enforcement to one chained turn, not one closure), and emit a sidecar warning when a turn ends with a non-empty pending slot so we can attribute fault correctly. A complementary lever is to surface the rejection inside the *same* turn by demanding a tool call from the model after every preview (e.g., `tool_choice="required"` budgeted to one extra round when a preview just landed) — but that's a deeper change.

**Iteration 6 (2026-04-21) — architectural reset (one-phase autonomous-writer surface; count + anchor-words gate; hub scope dropped):**

After five iterations of dispatcher patches and prompt-tuning failed to lift TP1 — and after Iteration 5's commit-enforcement made the cohort *worse* by introducing the cross-turn pending-preview leak — the structural problem became unambiguous: **the autonomous benchmark was being driven through a writer surface designed for human-in-the-loop ops.** Two-phase preview→commit makes the model emit a diff for an operator to read. With no operator present, the model often wrote that diff into its `message` field and stopped, because that is what the surface is asking for. No amount of prompt language ("do not ask the operator") or dispatcher patching ("reject anything but the matching commit") closed the class — they just shifted *where* the failure landed. Per Principle 2 of `.cursor/rules/engineering-principles.mdc` (Robust and Effective Over Cheap and Fast), the right move was to remove the surface that produced the symptom rather than continue patching it.

What landed in code (no live cohort yet):

- **`make_tool_dispatcher(..., autonomous_writes: bool = False)`** in `src/agent/planner.py`: when set, the dispatcher's handling of `append_timeline_row` and `write_corpus_file` becomes a **one-phase loopback wrapper**. Internally: dry-run preview → if `ok=False`, return preview error JSON unchanged → otherwise commit with the returned `confirm_token` and return only the commit-phase response. The model sees one tool call and one response; never sees `phase: "preview"`, `confirm_token`, or `next_call`. The writer's safety properties — allowlist, payload validators, `file_state_token` CAS — are unchanged; the contract just isn't *exposed* to the model in this mode. Two-phase remains the default for human-in-the-loop callers (`recap-write`, `npc-power-increase`, the REPL).
- **Simplified writer-tool schemas** when `autonomous_writes=True` (via `_planner_writer_tools_responses(autonomous_writes=True)`): `dry_run` and `confirm_token` are dropped from the parameter set; descriptions are rewritten to one-sentence direct-action statements (e.g., "Append a single timeline row… Commits immediately."). Legacy `dry_run` / `confirm_token` args from a model that emits them by mistake are silently stripped at the dispatcher.
- **Iteration-5 commit-enforcement code reverted** in `src/agent/planner.py` (the closure-local `pending_preview` slot, the `_commit_enforcement_identity` helper, the `enforcement_telemetry` parameter, and `tests/test_planner_commit_enforcement.py`).
