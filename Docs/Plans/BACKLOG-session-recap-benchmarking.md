## Why this is in backlog

We landed the recap writer (corpus writes + two-phase commit + `session-summary-from-notes` SKILL) before the next real session writeup arrived. The temptation was to invent synthetic inputs and benchmark immediately. We chose **not** to — synthetic inputs paired with synthetic golds tell you whether the skill is self-consistent, not whether it does what humans actually want.

When the next real raw → recap pair arrives, **Option A becomes free** (we can structurally validate against the real recap as gold) and **Option B becomes possible** (we can re-run the writer against the raw notes and diff against the human-authored recap). With one anchor pair in hand we can also tell whether Options C/D are even worth the build.

Until then: ship the writer behind the operator-approval gate, gather one real example, then come back here.

---

## Options considered

### Option A — Structural / contract gates

**Measures:** Mechanical correctness of the on-disk artifact, independent of prose quality.

**What we'd assert:**

- New recap file lives at `Session Recaps/Session NN - <slug>.md` under the chosen campaign hub.
- Frontmatter contains `title`, `document_class: play`, `canon_layer: campaign`, `campaign_id`, `session: N`, `origin_session: N`, `last_updated_session: N`, `source_class: observed_session_recap`.
- Body has a numbered TLDR section followed by long-form prose (heuristic: at least one numbered list and at least N paragraphs).
- Each appended `timeline.md` row has correct columns (Session | Beat | Recap file) and the `Recap file` cell matches the literal new filename.
- No edit landed on `*_character_dossier.md`, `character_seed.md`, or `*_statblock*.md` (allowlist already enforces server-side; gate confirms in artifact form).
- Corpus fingerprint changed exactly by the expected delta (recap file added, N timeline files mutated, nothing else).

**Cost:** Low. Pure assertions over the diff/artifact set; no LLM judge needed.

**Status:** Build first when one real pair lands. These gates are cheap and catch the largest class of regressions (misnamed file, lost frontmatter field, stray dossier touch).

### Option B — Time-rewind snapshot

**Measures:** End-to-end prose quality + path-discovery correctness against a known-good target.

**Shape:**

1. Take a real session N's raw notes (when we have them).
2. Snapshot the corpus *as it would have been before session N* — i.e. delete that recap file and revert the affected `timeline.md` rows.
3. Feed the snapshot + raw notes to the planner with `--allow-corpus-writes`.
4. Compare the writer's output recap to the human-authored original; compare the new timeline rows to what the human appended.

**What it catches:** Path mistakes (writing to wrong session number, wrong campaign hub), missing affected NPCs, prose drift relative to the GM's voice.

**Cost:** Medium. Needs paired raw-notes ↔ recap data, plus a snapshot/restore harness. The harness is a one-off script (`tools/eval_recap_rewind.py`?): given a target session, copy the corpus to a scratch dir, delete the target recap, revert timeline rows by line-range or by tagged anchors.

**Risk:** We don't currently have raw notes paired with the recaps already on disk. Without them, Option B can't run on existing corpus state — we'd be benchmarking against syntheses generated by Option C.

**Status:** Best end-to-end signal once we have one real pair. Build the snapshot harness around that first pair.

### Option C — Compress-then-expand

**Measures:** Round-trip fidelity (can the writer recover a recap from a synthetic compression of itself?).

**Shape:**

1. Take an existing recap file as gold.
2. Use a separate model call to summarize it into "synthetic raw notes" (terse, GM-scratch-shaped).
3. Feed those synthetic notes to the writer.
4. Compare the writer's recap to the original gold.

**What it catches:** Self-consistency of the skill (does the writer's prose match the format and beats it produces from a degraded version of its own output?).

**Risk:** The compressor's choices about what to omit silently shape what the expander is *capable* of producing. We'd be benchmarking the compressor as much as the writer. A well-tuned compressor masks writer weakness; a sloppy one creates phantom failures.

**Cost:** Medium. Two LLM calls per case (compress + expand) plus a diff/judge step.

**Status:** Defer. Only worth building if Options A + B are insufficient and we still need more cases than real raw-notes pairs can provide. Even then, treat results as "skill is self-consistent" evidence, not "skill matches GM intent."

### Option D — Mini-campaign

**Measures:** Same as Option B but with controlled, paired inputs we author on purpose.

**Shape:** Write a short toy campaign (~5 sessions) with explicit paired notes ↔ recap files. Use them as the standing benchmark suite — the writer should reproduce the recaps from the notes within tolerance.

**Cost:** High up-front (writing 5 sessions of believable game-table fiction is real work). Low recurring once authored.

**Risk:** Toy data may not surface the failure modes real session notes do (real notes are ungrammatical, contradictory, partial; toy notes will be cleaner unless we fight to keep them messy).

**Status:** Probably the right end state, but premature before we have one real raw-notes/recap pair to calibrate "messy enough."

---

## Decision (April 2026)

Punt all four to backlog. **First trigger:** the next real session writeup with raw notes preserved.

When that arrives:

1. **Build Option A** (structural gates) and run it against the real pair.
2. **Build the snapshot harness for Option B** using that pair as test case 0.
3. Re-evaluate whether we want Option C/D. Likely not unless real-pair throughput is too slow to sustain a useful benchmark.

Until then, the writer is gated by operator approval (two-phase commit + `apply` reply); a regression on disk is human-visible before commit, which is the strongest gate we can realistically have without ground truth.
