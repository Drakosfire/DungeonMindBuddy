## One question

Does one explicit bounded-follow-up instruction improve traversal and evidence-bounded answers on multi-hop, ambiguous, and no-path Graph questions, compared with the current graph-only Hermes route?

Six matched pairs were run using the same policy-resolved `openai-api` / GPT-6 Luna graph-only route, with fresh turn/retrieval sessions, model, scope, seed/candidate context, question, and system policy. Control used the existing question unchanged. Treatment appended one fixed instruction: “When the initial Graph result leaves a requested relationship unsupported or ambiguous, make up to two bounded follow-up Graph reads: use `object` on an accepted candidate only if needed to resolve its identity, then `neighborhood` with an accepted node target and depth 1 or 2. Stop when the path is supported; if the bounded reads leave no path or multiple candidates, state that clearly without inferring a connection.” Before either arm called the provider, system prompts were compared after normalizing only the fresh `retrievalSessionId`; raw prompt hashes were retained, and any other system-prompt difference would fail closed. The treatment sentence was the only user-prompt difference.

The six-case fixture distinguished three supplied-candidate cases from three discovered-candidate cases. Supplied candidates could be named in shared model context, but that context contained no relationship edge or path. Discovered candidates were revealed only by the fake's first `search`; neighborhood/object targets had to be supplied or returned as candidates earlier in the turn. Cases covered supplied and discovered two-hop paths, object identity disambiguation, same-label ambiguity, and supplied/discovered no-path. User questions named requested endpoints without disclosing expected chains. Gold edges, expected operation conditions, and abstention keys stayed out of model-visible questions, context, and tool descriptions. The fixed follow-up instruction appeared only in the treatment arm; gold expected chains stayed hidden from both arms.

## Stateful fake and evidence rules

The harness used Buddy's existing Graph-only Hermes route and replaced its retrieval dispatcher only inside the harness process. The stateful per-arm fake tracked accepted candidates, permitted operations, returned data, and turn phase. Initial `search` returned candidates and `outcome: partial` with no relationships; `object` returned only accepted synthetic identity attributes; fixture relationships were returned only by valid `neighborhood` requests, bounded by requested depth. The fake validated the model-visible `targets` and `depth` fields against Buddy's `ExpandGraphRetrievalRequest` schema and allowed only injected scope fields. It recorded operation order and returned IDs/attributes without dumping prompt/context into logs.

The per-answer hard gates required an `ok` turn, evidence for asserted relationships, no unsupported direction/nodes/edges, explicit unresolved target ambiguity, and bounded no-path language. A failed retrieval operation counted as traversal failure even when turn status was `ok`. The artifact preserves answer status separately from traversal success, plus per-arm calls, operation sequence, wall/provider durations, tokens, estimated cost, gates, raw answers, and synthetic evidence.
