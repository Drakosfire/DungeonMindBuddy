## 1. Decision

Persist a versioned Graph context receipt as a first-class nullable field on the canonical agent.turn record. Keep existing HistoricalReference and TurnProvenance.supporting_work meanings unchanged. In particular, the existing Graph reference continues to identify the managed World used for product scope. The new receipt separately records native Graph authority and the context/citation evidence.

**APP-STATE owner decision (2026-10-04):** accept this persistence and lifecycle boundary with the status and hash rules in §3 and §4. The operator authorized publication and bounded implementation. SERVER and DEMO retain their separate API and consumer ownership; no merge or operator-database authority is implied.

APP-STATE stores the immutable pre-dispatch context receipt, accepted-intent fingerprint, answer, versioned completion envelope, and lifecycle state. SERVER resolves and validates all Graph authority before submitting a receipt, then validates typed answer segments/citations against that frozen receipt before completion. APP-STATE validates typed shape, request/receipt consistency, write-once behavior, reference membership, and atomic persistence; it does not resolve a World binding or certify Graph claims.

The receipt contains context identities, digests, and retrieval statuses. It does not duplicate Plan Markdown, Graph assertion prose, source bodies, excerpts, or provider prompts.

## 2. Intent compatibility and Plan basis

Introduce an explicit request field named plan_context_policy with strict type PlanContextPolicyV1: schema=dmb_plan_context_policy_v1, policy=auto_plan_world. This is distinct from generic Graph query intent. For this fixed policy, submitted generic graph_request remains mode=none and graph_selection=null; those fields retain their existing meaning. Never infer the policy from Graph absence, route, or a null generic request.

Use a new submitted-intent schema for policy-bearing requests (discriminator dmb_agent_submitted_turn_intent_v2). It carries plan_context_policy and optional typed playable_target. The current request model types submitted_intent_v1 as optional, but ordinary new-turn acceptance in accept_turn rejects a missing intent; preserve that distinction and the existing replay/error behavior for older no-intent rows. For new accepted turns, require exactly one valid intent: v1 when no policy is present, or v2 for explicit auto_plan_world. Reject simultaneous v1 and v2 representations, require v2 only with explicit auto_plan_world, and reject v1 when that policy is present. V2 is valid only for a saved Plan turn with an exact caller Plan revision/digest, client_work_state saved_clean or saved_dirty, graph_request mode=none, and graph_selection=null. Preserve the existing v1 schema, validator, and fingerprint function for requests with no policy. No-policy v1 requests must preserve the exact existing canonical bytes and fingerprints; a new null policy key must not enter the v1 fingerprint input. Graphless completed/pending replay and authorization semantics remain unchanged.

The v2 fingerprint covers normalized caller intent, explicit policy version, message and existing surface/work intent, and optional playable target. Same-key changes to policy, message, surface/work basis, or card focus conflict; the existing turn_idempotency_fingerprint only covers World, user text, and provenance, so policy/card conflict detection must use the persisted v2 submitted-intent fingerprint. Native World ID, binding version, Graph revision, resolver output, receipt, provider output, and routing/CAS revisions are server-derived and are not caller intent. Persist the auto_plan_world submitted-intent digest in the new submitted_intent_fingerprint_v2 column. Preserve exact pre-change request_fingerprint, idempotency_fingerprint, and submitted_intent_fingerprint_v1 values for existing no-policy v1 requests. In particular, explicitly omit newly added default-null v2/policy fields from the legacy request_fingerprint payload; do not rely on model_dump defaults. Only explicit policy-bearing v2 requests use the new versioned submitted-intent fingerprint.

The server resolves and freezes the exact committed Plan basis: managed World ID, Plan document ID, object revision, WorkRevision UUID, revision number, and content SHA-256. Optional card focus remains a separate typed target pinned to that same basis. It must not be overloaded into selected_object. Mounted dirty editor bytes are neither submitted nor stored. Ask while the editor is dirty uses the exact committed Plan content; response and history disclose that unsaved edits were excluded.

Changing from explicit `auto_plan_world` to a policy-absent Plan-only Ask is never an automatic retry/downgrade. It requires a separate explicit user action and a new idempotency key.

## 3. Receipt v1

Proposed strict type: PlanWorldGraphContextReceiptV1, schema discriminator dmb_agent_plan_world_graph_context_receipt_v1.

Persist this receipt as a separate turn field; do not encode its native binding or citations into HistoricalReference. The existing managed-World reference retains its prior meaning.

Required top-level fields are schema, receipt_serializer_version=canonical-json-utf8-v1, context_receipt_sha256, plan_context_policy, plan_basis, playable_target, graph_authority, graph_packet, assembled_input, evidence_mode=metadata_only, and source_opened=false. These evidence-status fields are immutable and are not answer citations or completion outcomes.

- plan_basis: managed World ID, Plan document ID, object_revision, work_revision_id, revision_n, and content_sha256;
- native Graph World ID and active binding version;
- graph_authority: managed_world_id, native_world_id, binding_version, scope_mode=WORLD, campaign_id=null, admissibility_version, and exact graph_revision actually read;
- graph_packet: schema=dmb_plan_world_graph_packet_v1, packet_serializer_version=canonical-json-utf8-v1, selection_policy_version, evidence_sufficiency_policy_version, `retrieval_packet_sha256` over the bounded retrieved packet, sorted unique `candidate_assertion_ids`, `candidate_relationship_ids`, and `candidate_evidence_ref_ids`, retrieval_status (`complete` or `empty`), evidence_sufficiency_status (`sufficient` or `insufficient`), result_limit, coverage_status (`complete` or `incomplete`), truncated, and typed omission reasons. These candidate IDs and this hash describe retrieved/admitted candidates, not necessarily dispatched content;

- assembled_input: assembler_version, budget_policy_version, provider_model_name/version, tokenizer_name/version, full provider-envelope input token count, output-token reserve, context-window limit, `packet_disposition` (`included` or `omitted_insufficient`), `packet_disposition_reason` (null when included; `insufficient_evidence` when omitted), `dispatched_packet_sha256` (canonical digest of exactly included claim payload; null when omitted), exact sorted `dispatched_assertion_ids`, `dispatched_relationship_ids`, and `dispatched_evidence_ref_ids` (each a subset of retrieved candidate IDs; empty when omitted), per-source token accounting, included-history turn IDs and answer digests in order, and `assembled_input_sha256` of the exact canonical assembled provider envelope (full committed Plan, optional card focus, eligible history, user message, instructions/schema/tool overhead, and exact Graph payload or omission/status instruction);


Canonical packet digests use Python JSON bytes produced with ensure_ascii=False, sort_keys=True, separators=(",", ":"), allow_nan=False, then UTF-8 encoding, over the versioned packet envelope and selected claim/relationship/evidence-reference identities and values. Preserve Unicode code points without normalization. Candidate and dispatched identity arrays are sorted lexically and unique. Claim-bearing packet records are sorted by target kind then target ID. This order is part of packet_serializer_version. The retrieval_packet_sha256 identifies the exact bounded admitted retrieval set without persisting raw source bodies or duplicating the full Plan. The dispatched_packet_sha256 uses the same canonical JSON rule over exactly the dispatched claim payload and is null, with empty dispatched ID arrays, when packet_disposition=omitted_insufficient. `retrieval_status=empty` requires empty candidate arrays and `evidence_sufficiency_status=insufficient`; `retrieval_status=complete` may still have insufficient evidence. `truncated=true` requires `coverage_status=incomplete`; sufficiency is independent, so truncated/incomplete packets can be sufficient when admitted candidates meet the versioned evidence-sufficiency policy. Retries may rebuild and verify both retrieved and dispatched packet identities only from the original pinned revision and recorded policies; they must never repin. If exact revision, evidence, policy, or bytes cannot be reproduced, fail closed without changing the receipt.

`packet_disposition=omitted_insufficient` is required when evidence sufficiency is insufficient; its reason is `insufficient_evidence`, dispatched_packet_sha256 is null, and dispatched ID arrays are empty. `packet_disposition=included` requires sufficient evidence and a non-null dispatched_packet_sha256; the dispatched ID arrays identify exactly which candidate identities the packet contains. The receipt therefore records retrieved candidates and the exact packet actually sent as separate objects.

SERVER externally derives the whole-receipt lowercase 64-hex SHA-256 before persistence over the canonical UTF-8 JSON representation of the complete typed pre-dispatch receipt, using ensure_ascii=False, sort_keys=True, separators=(",", ":"), allow_nan=False, and no Unicode normalization. Exclude only `context_receipt_sha256` itself from its input. Include every other receipt field, especially source/evidence status, exact Plan and binding pins, `retrieval_packet_sha256` and retrieval/sufficiency/coverage/truncation statuses, packet disposition/reason, `dispatched_packet_sha256` and exact dispatched IDs, and `assembled_input_sha256` including provider model/tokenizer/version/output reserve. This digest does not include the later answer, completion envelope, or delivery-replay flag. Persist the retrieved-packet digest, dispatched-packet digest when included, and whole-receipt digest; they identify different objects. The assembled_input_sha256 identifies the entire provider envelope actually dispatched. APP-STATE validates digest shape and that completion references the identical receipt digest; it does not attest to SERVER's resolved Graph facts.

Hard failures before a valid immutable receipt exists do not create a receipt and never dispatch the provider or silently downgrade. SERVER returns a typed `PlanWorldGraphContextFailureV1` with schema `dmb_plan_world_graph_context_failure_v1`, status `pre_dispatch_failed`, failure_code from `managed_world_unresolved | native_binding_invalid | graph_read_failed | graph_revision_unavailable | graph_evidence_invalid | provider_envelope_over_budget | receipt_freeze_failed`, `provider_dispatched=false`, and `automatic_downgrade=false`. A policy-absent Plan-only Ask after such a failure requires a separate explicit user action with a new idempotency key.

After a valid pinned receipt is frozen, insufficient/empty evidence is a successful context outcome, not a binding/pin failure. For `plan_only_insufficient_evidence`, the receipt retains retrieval packet/status/digest, but the dispatched provider envelope omits all Graph claim payloads and includes an explicit Plan-only/omission instruction; it contains the full committed Plan and eligible history. The response/history clearly label the answer Plan-only and disclose truthful retrieval/coverage status. At completion, atomically store assistant_text, the unchanged receipt, and one nullable `agent.turn.completion` JSONB envelope. Its `answer_context_status` is exactly `graph_grounded | graph_grounded_partial | plan_only_insufficient_evidence | plan_only_graph_unused`; the entire completion envelope is null for legacy and policy-absent turns. The dimensions are independent: receipt evidence sufficiency/coverage/truncation record what was available; answer_basis is derived from segment kinds; answer_context_status records whether Graph claims were used and whether available grounding was sufficient/complete. `plan_only_insufficient_evidence` requires insufficient receipt evidence, no `graph_claim`, committed_plan basis, and null citation map. `plan_only_graph_unused` requires sufficient receipt evidence, no `graph_claim`, committed_plan basis, and null citation map. `graph_grounded` requires sufficient evidence, complete coverage, no truncation, at least one `graph_claim`, and a non-empty validated citation map. `graph_grounded_partial` requires sufficient evidence, incomplete coverage or truncation, at least one `graph_claim`, and a non-empty validated citation map; disclose incomplete coverage. Truncation alone does not imply insufficient evidence. A response-level `delivery_replay` boolean is separate and never changes or replaces the stored answer_context_status.

The typed completion envelope is `PlanWorldGraphCompletionV1`, schema `dmb_plan_world_graph_completion_v1`, stored in one nullable `agent.turn.completion` JSONB field. It contains `context_receipt_sha256`, `answer_basis` (`committed_plan` or `committed_plan_plus_world_graph`), `answer_context_status`, ordered `answer_segments`, and the validated `citation_map`. Segment categories are strict: `graph_claim` carries claim ID, text, target kind/ID, exact graph revision, and evidence-ref IDs; `plan_claim` carries text and the committed Plan content SHA-256 attribution; `proposal` is explicitly labelled as an invented/suggested idea; and `connective` is nonfactual transition text. SERVER derives answer_basis from segments and validates it as `committed_plan_plus_world_graph` when graph_claim segments exist, otherwise `committed_plan`; every plan_claim attribution must match the frozen Plan content digest. Both `plan_only_insufficient_evidence` and `plan_only_graph_unused` require committed_plan, no graph_claim segments, and null citation_map; the former requires insufficient receipt evidence and the latter sufficient receipt evidence. `plan_only_graph_unused` is output attribution only: the provider may have received usable Graph context, and this status does not claim to measure internal model attention. Graph-grounded statuses require committed_plan_plus_world_graph, sufficient receipt evidence, one or more graph_claim segments, and a non-empty validated citation_map with exactly corresponding claim IDs/target/pin/evidence references; `graph_grounded` additionally requires complete, untruncated coverage, while `graph_grounded_partial` requires incomplete or truncated coverage. The map entries retain `source_opened=false` and must reference only identities in the dispatched packet, not merely the receipt's broader candidate set. Keep assistant_text for existing turn display; replay returns the stored answer, segments, status and map unchanged. The response's delivery_replay flag is outside this stored envelope.

Whole provider-envelope accounting happens before receipt freeze. It includes provider model and version, tokenizer and version, output-token reserve, full committed Plan, eligible history, card focus, user message, all instruction/schema/tool overhead, and the exact Graph material allowed by the frozen sufficiency status. Insufficient Graph claim payloads are excluded; their omission/status instruction remains in the envelope and is covered by its digest. Require `provider_envelope_input_tokens + output_token_reserve <= context_window_limit`; if the complete envelope exceeds its budget, return a visible pre-dispatch failure; do not clip the Plan/history/envelope and do not dispatch. SERVER route/provider-envelope tests prove insufficient claims are not dispatched and that the digest matches the actual envelope. Output segments preserve distinctions among Graph-derived claims, committed-Plan material, creative proposals, and connective prose so co-GM narration need not present every statement as a Graph fact.

The envelope's citation-map schema is `dmb_graph_citation_map_v1`, bound by `context_receipt_sha256`; each entry contains `claim_id`, target_kind (assertion or relationship), target_id, exact graph_revision, a non-empty list of evidence_ref_ids, and source_opened=false. Entries correspond one-to-one to graph_claim segments. Each claim ID/target/pin/evidence reference must match the exact dispatched packet and its dispatched ID sets, which are subsets of the frozen receipt's retrieval candidates; merely retrieved-but-omitted evidence cannot be cited. SERVER proves semantic validity and APP-STATE stores the validated envelope unchanged. Do not infer citation alignment from arbitrary prose or treat a null map as proof of model-internal non-use. Graph evidence citations remain distinct from a future SourceCitationOpenedV1; metadata-only evidence cannot imply that source text was read, quoted, or verified.

## 4. Storage and lifecycle

Add nullable `agent.turn.graph_context_receipt` JSONB, nullable `agent.turn.completion` JSONB, and `agent.turn.submitted_intent_fingerprint_v2` (64-hex digest); expose their typed readback/projection. Keep every existing v1 request_fingerprint, idempotency_fingerprint, submitted_intent_fingerprint_v1 value and serialization byte-for-byte unchanged. Policy-absent accepted submissions preserve their exact current behavior and fingerprints; preserve the current missing-intent acceptance error for new turns and replay/error behavior for older no-intent rows. Explicit auto_plan_world submissions populate the new v2 fingerprint. Do not retag or recompute old rows. This is separate from supporting_work, selected_object, and legacy graph-reference columns. Existing rows have null receipt and completion; never infer native IDs, binding versions, packet hashes, or citations from old references.

The candidate additive migration adds exactly those two nullable JSONB values and the nullable v2 fingerprint. Database checks should permit null legacy values; for non-null receipt/completion require the corresponding schema discriminator and 64-hex context receipt digest. For completion, constrain `answer_context_status` to `graph_grounded | graph_grounded_partial | plan_only_insufficient_evidence | plan_only_graph_unused`. Both Plan-only values require `committed_plan`, no graph_claim segment, and JSON-null citation_map; either Graph-grounded value requires `committed_plan_plus_world_graph`, at least one graph_claim, and a non-empty map. Strict APP-STATE validation additionally checks status against receipt sufficiency/coverage, completion-to-receipt digest equality, exact segment/map correspondence, and receipt pin/reference membership.

Turn acceptance stores the policy-bearing intent fingerprint when present, exact server-resolved Plan/Graph context receipt, existing provenance, and pending turn under one APP-STATE transaction before provider dispatch. The receipt is immutable after acceptance and contains no answer citation map, because the answer does not exist yet. A same-key acceptance with a different typed intent, Plan/card basis, or receipt conflicts. The service must not accept an app-layer receipt whose policy, managed scope, Plan basis, or card focus disagrees with the submitted intent.

On success, one transaction validates the current claim/fence and persists assistant answer, unchanged context receipt, nullable typed completion envelope, terminal status, and completion time. SERVER validates segment categories, answer_basis, outcome status, and citations; APP-STATE validates the strict stored envelope and receipt-digest/pin/reference membership, then stores it atomically with assistant_text. The completion is null for graphless or policy-absent turns, and its citation_map is null for either Plan-only status. A failure cannot leave an answer without its matching completion/receipt or rewrite the accepted receipt. Existing claim expiry, fencing, and no-automatic-provider-redispatch semantics remain in force.

- Completed replay resolves the stored turn/intent before any current Plan, binding, Graph, or provider read and returns the original answer, immutable context receipt, and completion envelope, even if current bindings or heads have changed. `delivery_replay=true` is computed for that response only and does not mutate the stored envelope or outcome.
- Pending/interrupted retry first verifies that the original managed World still resolves to the recorded native World and binding version and that the exact recorded Graph revision remains available. A newer head alone is not drift. Rebuild/verify the packet at the original policy/version and digest. Any binding drift, unavailable pin, changed packet, or intent mismatch returns an explicit conflict/stale/unavailable outcome; it never updates the receipt or substitutes current context.
- Legacy rows with no receipt continue under existing graphless or generic-Graph rules. Do not synthesize a v1 receipt for them.

## 5. Owner boundaries

- APP-STATE owns typed persisted intent/receipt/completion shape, compatibility fingerprinting, same-key comparisons, write-once freeze, transaction boundaries, migration, and durable readback.
- SERVER owns request admission, managed-to-native resolution/fencing, exact-revision retrieval, canonical retrieved/dispatched packet construction and ordering, packet disposition, whole-receipt hash derivation, whole provider-envelope accounting, answer segment/basis/status/citation validation, hard failure and budget outcomes, and passing the frozen receipt before provider dispatch.
- MIND/DungeonMind owns native Graph revision, admissibility, claim/relationship, and evidence-reference authority. It confirms native R.3 admissibility/revision/evidence semantics; Buddy SERVER owns packet serialization and ordering. Its confirmed R.3 fixed World-scope/null-campaign/exact-revision bounded read is the v1 dependency; no new MIND endpoint is authorized here.
- DEMO owns explicit dirty-editor disclosure/fallback behavior and mounted display/history.
- PRIME owns publication acceptance, current-main/PR/lease census, topology, activation, and any merge/operational authority.

No provider, source-body opener, quote/passage citation, Graph write, Plan edit, Plan-to-Run, or operator acceptance is part of v1. No inferred receipt from legacy HistoricalReference data is allowed.

4. Fresh-service readback returns the exact versioned receipt and completion envelope. Same key/same intent yields the stored state; same key with changed policy/Plan/card intent conflicts.
5. Freeze-before-dispatch and atomic completion tests prove a receipt is durable before provider invocation and answer, status, segments, basis, map, and unchanged receipt persist atomically.
6. Completed replay performs zero Plan, binding, Graph, and provider reads and returns the stored completion envelope bound to the receipt digest. Pending retry uses the original tuple/revision/packet digest and never repins; unavailable original evidence fails closed.
7. SERVER supplies separate route/provider-envelope tests for distinct managed/native IDs, binding drift, exact revision and citation validation; hard pre-dispatch/budget failures never call provider or auto-downgrade; insufficient evidence uses Plan-only completion status and dispatches full Plan/history without Graph claim payload; sufficient-but-unused evidence remains Plan-only without being called insufficient; and sufficient truncated evidence uses partial grounded status with mapped claims. These are implementation acceptance requirements, not evidence that tests have run.
