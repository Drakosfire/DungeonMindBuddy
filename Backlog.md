## [DOING] Graph memory encounter/job extraction spike — real-data dogfood complete, Yellow verdict — captured 2026-07-01

**Context:** PRs #232–#244 built a gated runtime preview profile (`graph_extraction_profile = "category_encounter_job_preview"`) adding `quest`/`combat_encounter` node types, an optional `encounter_job_pass`, deterministic party participation attachment, and opt-in encounter/job edge guidance — validated first against a synthetic fixture (PR #242 Glowkindle). This entry captures the first **real-recap** dogfood against C1S1 (Stonebridge/Glowkindle rats), run via the actual runtime path (`recap_graph_preview_ingest.py::build_recap_graph_preview_bundle`), not a fixture bypass. Full writeup: `Docs/Reports/GRAPH-MEMORY-RUNTIME-ENCOUNTER-JOB-DOGFOOD-C1S1.md`.

**Insight:** Verdict is **Yellow — shape promising, refinement needed**. The core taxonomy decision holds on real data: `quest` and `combat_encounter` nodes were correctly typed, evidence-backed (101/101 resolvable, 0 full-text-fallback), and got a `results_in` edge back to the quest the fixture never even tested. Party attachment was clean — zero duplicate PCs, zero duplicate party nodes, and the model correctly self-suppressed re-extracting the PC roster once context anchors existed. Two concrete gaps, independent of each other: (1) **quest overgeneration** — 1 of 2 quest nodes ("follow directions to the brewery") is travel flavor, not a real job, and deterministic party attachment amplifies it into an extra edge rather than filtering it; (2) **cross-class node duplication is structural to category-decomposed extraction, not incidental** — 7 of 42 raw nodes (17%) on this one recap are the same real-world thing (Stone Bridge, the pub, the brewery, giant rats, the cat owl, the gnomes, the boulder) independently rediscovered by 2–3 different category passes, and every single collision landed in `cross_class_blocked_nodes` rather than the narrow place+collective auto-merge — real collisions are almost always 3-way, which the existing policy doesn't cover. This is the same open question already queued for the Prime Design agent, now with a concrete 7-group regression fixture. **Separately, and unrelated to the encounter/job question:** found and root-caused a paragraph-segmentation boundary bug — `_split_recap_paragraph_spans`'s regex requires a paragraph to end at a blank line or absolute string end, so a file ending in exactly one trailing newline (i.e. every normally-saved recap) silently drops its *final* paragraph from every extraction pass. On C1S1 that dropped paragraph seeds the next session's antagonist (the shatter mage's tower spider). This affects `current_default` identically, not just the new profile.

**Action:** Added `evals/graph_memory_layer/run_encounter_job_dogfood.py`, a thin CLI wrapper around the existing `build_recap_graph_preview_bundle` service call (no extraction-behavior change) so the runtime profile can be dogfooded from the command line. Four follow-up PRs identified, ordered by directness, each independently small in scope: (1) fix the paragraph-segmentation trailing-newline bug — urgent, blocks trustworthy dogfood on any other recap; (2) refine `encounter_job_pass` salience to exclude generic travel intent from `quest`; (3) extend cross-class identity/consolidation beyond the 2-way place+collective rule, using this run's 7 blocked-collision groups as a fixture; (4) fix `candidate_validation_report.json`'s evidence-count logic (it only checks a top-level `evidence_refs` array that this schema never populates, so it falsely reports 0/101 evidence while the manifest `health` block correctly reports 101/101).

## [READY] Decide citation rendering format (HTML comments inline vs. frontmatter `citations:` block vs. markdown footnotes) before retrofitting render artifacts — captured 2026-04-23

**Context:** The citation-grounded corpus architecture (`Docs/Design/DESIGN-citation-grounded-corpus-architecture.md`) separates capture-layer (structured facts with `SourceAnchor`s, machine-readable) from render-layer (markdown prose for the GM, human-readable). Capture-layer storage is settled (`SourceAnchor` dataclass, `evidence_units` schema). Render-layer is not: when the system writes a paragraph into an NPC hub citing facts F1, F2, F3, what does the markdown look like? Three candidate shapes have meaningfully different ergonomics for the GM, the linter, and the LLM that re-reads these documents:

1. **Inline HTML comments** — `<!-- cite: fact_id_F1 -->` immediately before/after the prose. Invisible in rendered markdown, fully machine-readable, easy to parse with a regex. Cost: clutters the source; requires the GM to mentally filter when editing; if the GM moves the prose, the citation marker can desync silently.
2. **Frontmatter `citations:` block** — a YAML list at the top of the file mapping each citation id to the fact id and source anchor. Prose body references citations by number (`[^1]` / `[1]`). Clean source; survives prose edits well; requires a build step to verify reference numbers are in range. Familiar to anyone who's used Pandoc.
3. **Markdown footnotes** — `[^F1]` inline in the prose, footnote definitions at the end of the file pointing at the source anchor. Renders as visible footnotes in most markdown viewers (could be a feature for the GM, a wart for prose flow). Standard markdown; broadly tooled; visually noisy in the source.

The choice has knock-on effects on the lint contract, the planner's render prompt, and how the `live_planning_collab` workflow attaches citation evidence. Picking now (before retrofitting any existing render artifact) prevents shipping two incompatible variants and having to migrate.

**Action:** (1) Mock up each of the three shapes on a real existing render artifact (pick one of the C1 PC hubs, e.g. `corpus/eldyrwild-markdown/Longmont Campaign/Campaign 1/PCs/baergrom/baergrom_character_dossier.md`) — same prose, three different citation styles — and read each through GitHub's markdown viewer + a plain text editor.
